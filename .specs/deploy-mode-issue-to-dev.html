Purpose

Add a --deploy flag. Without it the runner behaves as today. With it, after the tickets are built the runner also:

  1. opens a pull request,
  2. watches the code review and CI, and fixes what they raise,
  3. merges the PR when the review passes, resolving any merge conflicts,
  4. watches the Dev deployment that the merge triggers, until the work is live in Dev.

Definition of Done: the issue passes its acceptance criteria, the PR passes code review, the merge succeeds, and the Dev deployment succeeds. Everything else is a fail.

Problem

Today a run finishes the moment it opens a pull request (orchestrator._open_pull_request). Four things are missing:

  • Acceptance criteria are never checked. The planner reads the issue once. Nothing maps criteria to tickets, and nothing checks the finished change against them. For #110 three criteria were only partly tested. Woodside/ai-maint issues keep their criteria under ## Acceptance criteria as checkboxes (15 of the last 22 issues), and many criteria can only be checked in Dev ("In Dev at 1920x1080 …").
  • The review is ignored. The Woodside/ai-maint ruleset "Copilot review for default branch" requests a Copilot review when a PR opens, with review_on_push: false. The runner never reads it, never fixes its findings and never asks for a re-review.
  • Nobody merges. Woodside/ai-maint allows squash merges only and needs 0 approvals. A merge is a single permitted step that the runner never takes.
  • Nobody watches Dev. dev-deployment.yaml runs on a push to main (with a paths filter), deploys to environment development and records a GitHub deployment. Runs can be cancelled when a newer merge supersedes them (run 37261581216, ea9e9377).

The PR body also says Closes #n, so GitHub closes the issue at merge, even if the deployment fails afterwards.

Solution

Add a delivery stage machine that runs after the ticket loop when --deploy is set. It reuses what the runner already does well: deterministic gates around every agent step, saved state for each stage so a stopped run resumes, and bounded rounds.

  • Criteria first. Parse the acceptance criteria into AC1..ACn. The planner must map every criterion to tickets (checked in tests) or to a Dev check (checked after deployment). Unmapped criteria reject the plan. Before the PR opens, a read-only acceptor agent judges every test-checked criterion against the whole change.
  • Dev checks are written before merge and must fail first. For criteria checked in Dev, an acceptance.tester writes an executable check before the PR opens. Run against Dev now, it must fail, since Dev does not have the change yet. After the deployment it must pass. This is the tester's red-then-green rule applied to Dev.
  • Review loop. Poll the PR. The review passes only when a fixed rule holds (Phase 4). Each finding goes to a reviser agent under the same guards as the coder: frozen ticket tests, a regression run, safe paths, no force-push. Then the runner replies to the thread, resolves it and requests a new Copilot review.
  • Merge. If the PR is behind or conflicted, merge the base into the branch. A resolver agent fixes any conflicts. Conflict markers, ticket tests and the regression suite are checked in code. Every new head goes back through review. Merge with the repository's permitted method and --match-head-commit.
  • Deploy watch. Find the deployment run for the merge commit and follow it. It succeeds only when a GitHub deployment to the configured environment reports success for a SHA that contains the merge commit. That covers runs that are superseded or cancelled.
  • Close-out. Run the Dev checks. Tick each criterion that passed in the issue body. Close the issue only if every gate passed. The PR says Refs #n in deploy mode, so the merge alone never closes the issue.

2. Review gate rule

def review_passed(pr, head_sha, cfg) -> bool:
    checks = check_runs(head_sha)
    if not checks or any(c.status != "completed" for c in checks):
        return False                                  # still running
    if any(c.conclusion not in ("success", "neutral", "skipped") for c in checks):
        return False                                  # failing check = finding
    bot = [r for r in reviews(pr) if r.author == cfg.review_bot]
    if not bot or bot[-1].commit_id != head_sha:
        return False                                  # no review on this head yet
    if comments_in_review(bot[-1]) > 0:
        return False                                  # new findings on this head
    if any(not t.is_resolved for t in review_threads(pr)):
        return False                                  # older findings left open
    latest_human = latest_review_per_human(pr)
    if any(r.state == "CHANGES_REQUESTED" for r in latest_human):
        return False
    if approvals(pr) < protection.required_approving_review_count:
        return False                                  # wait for a person
    return True

  • [x] Findings are the unresolved review threads (GraphQL reviewThreads: path, line, body, thread id) and failing checks (name and the tail of the log from gh run view --log-failed), plus any CHANGES_REQUESTED body.
  • [x] The reviser agent gets all current findings in one prompt and edits the worktree. def deployed(merge_sha, cfg) -> Deployment | None:
    for d in deployments(environment=cfg.environment):      # newest first
        if not is_ancestor(merge_sha, d.sha):
            continue
        status = latest_status(d)
        if status.state == "success":
            return d                     # deployed_sha = d.sha
        if status.state in ("failure", "error"):
            return None                  # caller fails the gate
    return None                          # keep polling until timeout

Notes

Definition of Done as gates

GatePasses whenFail exit
ticketsEvery ticket is done, none blocked, and the regression suite passes.3 (blocked), 4 (budget), 1 (abort)
criteria_testsEvery tests criterion is met with cited tests that run and pass.5
reviewreview_passed() holds on the head that gets merged.6
mergeThe PR is MERGED at the reviewed head, and merge_sha is saved.7
deployA deployment to the configured environment reports success for a SHA that contains merge_sha.8
criteria_devEvery frozen Dev check prints ACCEPT-PASS against Dev.5

A stop request (Ctrl+C, exit 130) is not a failure verdict. The run state is saved, and re-running the same command resumes at the saved stage.

Defaults chosen in this plan (change before building if wrong)

  1. Issue closes only after the DoD passes. In deploy mode the PR says Refs #n, and the runner closes the issue at the end.
  2. Declining a review comment needs a read-only verifier to agree. Otherwise the thread stays open and the review gate cannot pass.
  3. A failed deploy or Dev check after merge is not auto-reverted. The runner reports, comments and exits non-zero. Reverting is left to a person, because a revert is itself a merge to main that triggers another deploy. A hotfix loop is a possible follow-up.
  4. A merge that triggers no deploy (because of the paths filter) fails by default. dispatch_if_not_triggered is opt-in.
  5. Criteria checked in Dev need dev_check_cmd. Without it preflight fails. For Woodside/ai-maint this means an Edge and Playwright harness (pw-win with an Entra sign-in) on the machine that runs the runner.
  6. Required human approvals (currently 0 on Woodside/ai-maint) are waited for up to review_timeout_min. The runner never approves its own PR.
  7. Copilot review counts as clean when its latest review on the current head has zero comments and no thread is unresolved. GitHub only ever marks it COMMENTED, as on Woodside/ai-maint#344.

Facts this plan relies on (checked 2026-10-05)

  • Woodside/ai-maint allows squash merge only. delete_branch_on_merge is false and allow_auto_merge is false. Branch protection requires 0 approvals and has no required status checks.
  • Ruleset 21702720 "Copilot review for default branch" sets copilot_code_review with review_on_push: false and review_draft_pull_requests: true.
  • dev-deployment.yaml runs on a push to main under a paths filter. Its jobs are ci, then development, which calls deploy-web-application-base.yaml with environment development and concurrency group application-dev. Deployments are recorded per SHA (for example 6854019104 for 9a17d7f0, the merge of #344).
  • Local gh is 2.46.0. Re-requesting the Copilot review goes through the REST API.

Risks

  • Wall-clock time. A review takes minutes and a deploy about 6 minutes on Woodside/ai-maint. With review rounds a run can exceed an hour. Every wait is bounded and resumable, and the credit budget only counts agent calls.
  • Shared main. Other merges can land between the review gate and the merge. --match-head-commit protects the head. Base movement is handled by the behind/dirty loop, and deploy supersession by the ancestry rule.
  • Authority. The runner merges to main and so triggers a deploy, using the operator's gh token. Preflight checks write access, and every merge is logged in the DoD comment with the gate evidence that allowed it.
  • Agent dismissing findings. This is limited by the verifier agreement rule, and every decline is listed in the DoD comment for a person to audit.
